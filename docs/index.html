FlyRank ML Internship Capstone

Refresh / Content Opportunity Scoring

A transparent, ranked review system for deciding which pages deserve a human refresh decision.

Abstract

This project studies a practical operational question: which anonymized content pages should an editorial team review next for refresh or maintenance? We use the public FlyRank starter dataset to build a transparent ranking system that combines stale-content, demand, and visibility signals. We compare a baseline rule against several learned models on a grouped client holdout, then choose the model that best helps prioritize a small review queue. The result is a ranked action engine for human triage, not a claim that content refresh causes changes in Google rankings or traffic. The analysis is designed to support editorial decisions, not prove causal search impact.

Problem statement

The decision supported by this work is narrow and operational: when an editorial team has a backlog of content pages, which ones are worth reviewing first for refresh, rewrite, or monitoring? The work does not claim to know why a model works in the broader search ecosystem. It instead gives a ranking and reason-code system that helps a team triage pages with the highest review value under a transparent, auditable rule set.

Data

The analysis uses the bundled anonymized starter dataset at data/raw/content_refresh_anonymized.csv, which is a 30,000-row content snapshot for pseudonymized clients. The data dictionary describes the column meanings and caveats, especially the fact that rate columns are percentages and that trend-derived labels must not be used as model inputs. The project is intentionally public-safe: no client names, no URLs, no domains, no raw queries, no credentials, and no private search data are used.

We exclude label-derived and outcome-window columns from the feature set, including fields that directly encode the target or the recent trend window. This makes the model a review aid rather than a claim about the algorithm. The feature set is restricted to content metadata, recency, word count, and public-safe opportunity variables that are available before the review decision is made.

Methodology

We compare a transparent baseline with multiple learned models on the same grouped client holdout. The baseline rule is: review pages that are both stale and visible. We score visibility using impression volume and combine it with content age and recency to create a human-readable priority score. We then compare the baseline with logistic regression, random forest, extra trees, and histogram gradient boosting using the same test rows and the same label: a retrospective decline indicator defined from trend direction.

The key validation choice is a grouped client split. Rows from the same pseudonymized client are kept together in the same split to reduce the risk that the model memorizes client-level patterns rather than learning more general ranking behavior. We report the base rate next to every metric and treat the results as a held-out ranking comparison, not as causal proof.

Validation setup

  • Rows scored: 30,000
  • Declining-label rows: 16,262
  • Declining-label rate: 0.542
  • Split strategy: client_holdout
  • Target: is_declining_label

Results

The primary metric for this task is precision@50, because the operational question is not “is the page generally declining?” but “which 50 pages deserve an editorial review first?” On that metric, the random forest model performed best on the client-grouped holdout, with a strong lift over the transparent baseline.

Limitations and honest framing

This is a retrospective, decision-support analysis rather than a causal experiment. It does not prove that refreshing content causes traffic gains or ranking improvements. It also operates on a public, anonymized starter slice rather than the full warehouse, and the label is defined on a historical trend snapshot. Because of that, the appropriate language is observed, directional, and operational: the model helps a team rank pages for review, but it does not establish a causal mechanism or claim algorithmic certainty.

Ranked recommendations

  1. Review the highest-ranked stale and visible pages first.
  2. Use reason codes to explain why a page was selected for review.
  3. Move low-volume stale pages to a monitoring queue unless there is independent editorial evidence of opportunity.
  4. Re-run the queue after each content update cycle using the same validation and label logic.
  5. Use the ranked queue as a triage aid, not as an automatic publishing decision.

Reproducibility

The analysis is reproducible from the repository. The core source is the starter CSV, the baseline and model scripts, and the capstone notebook. The model report and sample refresh queue are already generated in the repo, and the full results workflow can be rerun from the notebook or the project scripts.
